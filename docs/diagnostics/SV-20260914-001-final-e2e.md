# SV-20260914-001 — Validation E2E finale SFTP

Date : 15 septembre 2026 (Europe/Paris)
Branche : `diagnostic/sftp-r8-validation`

**Statut : PASS — validation SFTP réelle de bout en bout sur Redmi Pad 2 Pro et NAS réel.**

Ce complément clôt la validation fonctionnelle du correctif R8/BouncyCastle documenté dans `SV-20260914-001.md`.

## Périmètre validé

Environnement réel :

- Redmi Pad 2 Pro, device ADB `02bfb398d603` ;
- NAS Asustor `192.168.1.26:22` ;
- compte SFTP réel `jellyfin` ;
- clé hôte ECDSA épinglée : `0e:84:2c:b6:68:58:4b:65:f0:f4:ac:72:b3:28:83:df` ;
- sonde minifiée `:sftp-e2e` construite avec R8 ;
- vrai `SshjNasSftpClient` des modules `:data` / `:domain` ;
- vraies règles de production `app/proguard-rules.pro` incluant le keep BouncyCastle ;
- répertoire distant de validation : `.` (home SFTP du compte).

La sonde a été exécutée sans installation Android, via `CLASSPATH=/data/local/tmp/sv-sftp-e2e.apk app_process ...`.
L'application principale `com.streamvault.app.custom` n'a pas été remplacée, désinstallée, vidée ou modifiée.

## Résultat brut final

```text
RESULT=SUCCESS directoryVerified=true writeVerified=true
```

Ce résultat prouve dans le même appel réel :

1. connexion TCP/SSH au NAS ;
2. négociation SSH sur le build minifié ;
3. décodage de la clé hôte ECDSA avec BouncyCastle après R8 ;
4. validation stricte de la clé hôte épinglée ;
5. authentification réelle du compte `jellyfin` ;
6. ouverture du sous-système SFTP ;
7. `stat` du répertoire distant `.` ;
8. création d'un fichier `.streamvault-write-test-<UUID>.tmp` ;
9. écriture d'un octet ;
10. suppression du fichier temporaire ;
11. retour `Success(directoryVerified=true, writeVerified=true)`.

## Contrôles d'authentification

Avant le PASS E2E, les mêmes identifiants ont été vérifiés depuis le Mac :

```text
sftp -P 22 jellyfin@192.168.1.26
Connected to 192.168.1.26.
```

Puis avec authentification SSH `password` explicitement forcée :

```text
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no -p 22 jellyfin@192.168.1.26 true
```

La commande a terminé sans erreur. Le NAS accepte donc bien l'authentification `password` pure.

Deux essais précédents de la sonde avaient retourné :

```text
RESULT=FAILURE error=AUTHENTICATION_FAILED
```

Ils utilisaient une saisie manuelle du secret à l'intérieur du shell Android. Le PASS final a été obtenu en saisissant le secret masqué sur le Mac puis en le transmettant par stdin au shell Android, qui l'a exporté uniquement pour le processus `app_process`.

Le PASS final démontre que `SSHJ.authPassword()` et le NAS sont compatibles. Les échecs précédents sont donc spécifiques au chemin de saisie/transmission manuelle du secret dans le shell Android ; leur mécanisme exact n'a pas été approfondi car il n'appartient pas au chemin normal de l'application.

## Protection du secret

- aucun mot de passe n'est présent dans le dépôt ;
- aucun mot de passe n'est écrit dans les arguments de commande ;
- le secret a été saisi avec écho désactivé sur le Mac ;
- il a été transmis par stdin ;
- la sonde lit `SV_SFTP_CREDENTIAL` puis le convertit en `CharArray` ;
- le `CharArray` est effacé dans un `finally` ;
- la variable shell distante est supprimée après exécution ;
- aucune sortie de test ne contient le secret.

## Conclusion

La cause initiale `UNKNOWN` du release minifié est bien corrigée par la règle BouncyCastle ajoutée à `app/proguard-rules.pro`.

La validation ne se limite plus au handshake ou à la confirmation de clé : **l'ensemble du chemin SFTP réel fonctionne maintenant sur la Redmi et le NAS réel, jusqu'au test d'écriture et de suppression distante.**

Le prochain contrôle fonctionnel, distinct de ce diagnostic, consiste à tester le répertoire distant réellement configuré dans StreamVault s'il diffère de `.`. Avant tout remplacement de l'application principale, la signature du candidat devra être comparée à celle de l'APK actuellement installé afin de préserver les données utilisateur.
