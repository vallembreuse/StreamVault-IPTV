# SV-20260914-001 — Diagnostic SFTP Android / R8

Date : 15 septembre 2026 (Europe/Paris). Branche : `test/nas-lot1-sftp-hardening`.

**Statut : PASS — cause démontrée, correctif appliqué, validation minifiée sur Redmi.**
Déploiement dans l’application principale non effectué.

## Cause démontrée

R8 supprime les classes BouncyCastle découvertes par noms construits dynamiquement,
notamment `org.bouncycastle.jcajce.provider.asymmetric.EC$Mappings`.
Le provider embarqué est créé et enregistré, mais ses services cryptographiques
manquent : **24 services**, sans fabrique de clés `ECDSA`.

La connexion échoue à **CONNECT**, dans `ssh.connect()`, au décodage de la clé ECDSA
du NAS, **avant** l'appel au vérificateur de clé hôte. La chaîne d'exceptions est :

```text
net.schmizz.sshj.transport.TransportException
  -> net.schmizz.sshj.common.SSHException
    -> net.schmizz.sshj.common.SSHRuntimeException
      -> java.security.GeneralSecurityException
        -> java.security.NoSuchAlgorithmException: ECDSA KeyFactory not available
```

Le message des exceptions enveloppantes est
`java.security.NoSuchAlgorithmException: ECDSA KeyFactory not available`.
`observedTrust=null`, `verificationRejected=false` : aucune clé n'a été observée
par le vérificateur. Cette chaîne ne correspond à aucun cas de `toDomainError()` ;
le résultat est donc `NasSftpError.UNKNOWN`.

Le debug conserve ces classes : les tests précédents passent. Leur suppression par
R8 explique la différence avec le release. Le fingerprint lui-même n'est pas la cause.

4. Mini APK Android compilé avec **AGP 8.10.1 / R8**, **SSHJ 0.40.0**, **BC 1.80.2**,

5. Avec la règle candidate : 1 606 services et `ECDSA=true` ; confirmation de la vraie

Ces processus n'utilisent ni les préférences ni les identifiants de StreamVault.
Les DEX installés ont été testés directement, sans supposer qu'ils sont identiques
au release local ou que son mapping décrit tout l'APK installé.

### Hypothèse du provider racine réfutée

Dans **les deux APK**, R8 a correctement remplacé le `Class.forName` du provider
racine par `const-class LY9/b;`, suivi de `getDeclaredConstructor/newInstance`.
Le nom `org.bouncycastle.jce.provider.BouncyCastleProvider` reste dans les messages
de journalisation ; sa présence ne prouve pas un échec de chargement.

En revanche, le bytecode de `BouncyCastleProvider.loadServiceClass()` construit
`package + algorithm + "$Mappings"`, appelle `ClassUtil.loadClass()`, puis
`newInstance()` et `configure()`. Le DEX conserve cette construction dynamique,
mais `usage.txt` confirme la suppression de `EC$Mappings`, `MD5$Mappings`,
`SHA256$Mappings`, `AES$Mappings`, entre autres.

Les JAR SSHJ 0.40.0 et bcprov-jdk18on 1.80.2 inspectés ne contiennent pas de règles
consumer ProGuard. `-dontwarn org.bouncycastle.**` ne conserve aucune classe.

La comparaison `provider.javaClass == BouncyCastleProvider::class.java` continue de
fonctionner après renommage. SSHJ tente ensuite d'enregistrer BC ; ses contrôles
MD5/DH peuvent échouer quand les services ont été supprimés, entraînant son repli
sur la sélection JCA par défaut. Cette sélection ne trouve pas non plus `ECDSA`.

## Correction

Une seule règle de production ajoutée à `app/proguard-rules.pro` :

```proguard
-keep,allowoptimization class org.bouncycastle.jcajce.provider.** {
    public <init>(...);
}
```

Elle préserve les noms et constructeurs des déclarations d'algorithmes et des
implémentations JCA chargées par réflexion. Les méthodes restent optimisables.
Elle couvre le mécanisme de découverte du provider, plutôt qu'un seul algorithme
négocié par ce NAS. Aucun keep global de SSHJ ou de tout BouncyCastle.

Aucun changement du client Kotlin, des algorithmes SSH, du compte NAS ou de la
configuration SSH du NAS. Les clés inconnues exigent toujours une confirmation ;
une empreinte différente doit toujours produire `HOST_KEY_CHANGED`.

### Incidents distincts pendant les tests

Certains essais rapprochés ont reçu `Connection reset` pendant la lecture initiale
SSH, avant la vérification de clé ; ils ne constituent pas des validations réussies.
Une pause de plus de deux minutes a permis de retrouver le résultat attendu.
Une pénalisation temporaire côté serveur est plausible, mais non démontrée :
aucune modification de sa configuration n'a été effectuée et aucun diagnostic
seccomp antérieur n'a été recommencé.

L'installation du nouveau package `com.streamvault.sftp.diagnostic` a été refusée
par Android (`INSTALL_FAILED_USER_RESTRICTED`). Les mini APK ont donc été exécutés
sans installation via `CLASSPATH=... app_process /system/bin probe.Runner`.
Ce mode utilise le vrai runtime Android et le vrai réseau, mais pas le cycle de vie
ni l'UID de l'application principale.
